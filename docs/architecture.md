# 架构设计与选型理由

## 为什么 Java（治理面）+ Python（编排面）异构拆分？

- **治理面是企业级后端**：多租户、RBAC、配额计量、灰度发布、审计——Java/Spring 生态成熟稳定，工程化能力最强
- **编排面要跟生态**：LangGraph、MCP、各类模型 SDK 的 Python 生态最完整，迭代最快
- 两者通过 HTTP/gRPC 解耦，可独立演进、独立扩缩容

## 为什么 LLM 网关独立于 API 网关？

| 关注点 | API 网关 | LLM 网关 |
|---|---|---|
| 路由 | 按路径/服务 | 按模型能力/成本/可用性 |
| 限流 | QPS | token 预算 + QPS 双维度 |
| 降级 | 服务熔断 | 模型级降级（主模型→备用模型） |
| 计费 | 无 | 按 token 成本核算 |
| 缓存 | HTTP 缓存 | 语义缓存 |

## 长任务断点续跑设计

核心思路：**检查点表 + 可靠消息**，本质与分布式事务的可靠消息模式同源。

1. Agent 每执行一步，LangGraph Checkpointer 将状态落 PostgreSQL
2. 任务状态机（RUNNING/PAUSED/FAILED/COMPLETED）落业务库
3. 服务重启后，调度器扫描中断任务，从最近检查点恢复执行
4. 工具调用层保证幂等（idempotency-key），重放不产生副作用

## 存储选型

- **pgvector 而非 Milvus**：单机阶段少一个组件，面试可对比两者取舍；数据量大后可平迁
- **Redis**：会话窗口缓存 + 令牌桶限流 + 分布式锁
- **MinIO**：文档/产物文件对象存储，S3 兼容
